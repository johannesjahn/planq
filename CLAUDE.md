# planq

TypeScript + Bun + Effect API. User register/login backed by SQLite via Drizzle, Swagger/OpenAPI docs auto-generated from the `HttpApi` definition. ESLint + Prettier configured. `web/` is a **separate package** holding the React frontend — see the section at the bottom.

## Run / check

```bash
bun run dev         # start with --watch
bun run start        # start once
bun run test          # bun test
bun run typecheck    # tsc --noEmit
bun run lint         # eslint .
bun run format       # prettier --write .
bun run openapi:generate   # regenerate web/api.json from the HttpApi definition
```

Env vars (see `.env.example`): `PORT` (default 3000), `DB_FILENAME` (default `planq.sqlite`), `JWT_SECRET` (**required** outside `NODE_ENV=test` — the server fails to start without it, see gotcha below), the `RATE_LIMIT_*` family and `TRUST_PROXY` (all optional, defaults in `src/api/RateLimiter.ts`), `MAX_REQUEST_BODY_BYTES` (optional, default 8 KiB, in `src/api/BodyLimit.ts`), `HSTS_MAX_AGE_SECONDS` (optional, default one year, in `src/api/SecurityHeaders.ts`).

## File map

- `src/domain/User.ts` — Effect `Schema.Class` models: `User` (`id`, `username`, `createdAt`), `RegisterPayload`, `LoginPayload` (both `username`+`password`, no email). `UserId` is `Schema.UUID.pipe(Schema.brand("UserId"))` — a branded UUID string, not a number. Also exports `normalizeUsername` (`trim().toLowerCase()`), the single definition of the case-insensitive-username rule — used by `AuthLive` for the `users.usernameLower` column and by `RateLimiter` for the lockout key. Tagged errors `UsernameAlreadyInUse` (409), `InvalidCredentials` (401), `Unauthorized` (401), status set via `HttpApiSchema.annotations({ status })` as the 3rd arg to `Schema.TaggedError`.
- `src/domain/Auth.ts` — `CurrentUser` (`Context.Tag`), `JwtConfig` (+ `JwtConfigLive` reading `JWT_SECRET`, no default outside tests), `hashPassword`/`verifyPassword`/`verifyPasswordConstantTime` (`Bun.password`, argon2id; cost params turned down under `NODE_ENV=test`), `signToken`/`verifyToken` (`jose`, HS256, 2h expiry; JWT `sub` claim is the UUID string, validated against `UserId` via `Schema.is` on verify so a malformed/foreign `sub` fails closed as "invalid token" rather than being coerced).
- `src/db/schema.ts` — Drizzle table def: `users` (`id` text PK, populated via `$defaultFn(() => crypto.randomUUID())` — no `autoIncrement`, ids are UUID v4 strings; `username`, `usernameLower` unique, `passwordHash`, `createdAt`). Usernames are case-insensitive: `username` stores the casing that was typed (and is what the API returns), `usernameLower` stores `normalizeUsername(username)` and carries the `UNIQUE` index — see gotcha below on why this isn't `COLLATE NOCASE`. `createdAt` defaults to `sql\`(strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))\``(real ISO 8601 UTC, not SQLite's bare`datetime('now')`which omits`T`/`Z`). Source of truth for `drizzle-kit generate`.
- `src/db/Database.ts` — `Db` = `Context.Tag` for a `BunSQLiteDatabase<typeof schema>`. `DatabaseLive` is `Layer.scoped`: opens `bun:sqlite` on `DB_FILENAME`, wraps it with `drizzle()`, runs pending SQL migrations from `drizzle/` via `drizzle-orm/bun-sqlite/migrator`'s `migrate()` on every startup (idempotent — tracks applied migrations in its own bookkeeping table), and closes the connection via `Effect.acquireRelease` when the scope closes.
- `drizzle/` — SQL migrations generated by `bun run db:generate` from `src/db/schema.ts` (config in `drizzle.config.ts`). Committed to the repo; regenerate after every schema change and commit the new file alongside it — CI regenerates and fails if that produces anything, so a schema change that skips `db:generate` can't merge. This replaced the old hand-rolled `CREATE TABLE IF NOT EXISTS` bootstrap. `0001` is hand-completed (drizzle-kit can't emit a backfill for a new `NOT NULL` column) — a migration that's already applied elsewhere is immutable history, so fix such a thing forward in a new migration rather than editing it.
- `src/domain/RateLimit.ts` — the `TooManyRequests` tagged error (429), carrying `retryAfterSeconds`.
- `src/domain/BodyLimit.ts` — the `PayloadTooLarge` tagged error (413), carrying the `maxBytes` that was exceeded.
- `src/api/Api.ts` — the `HttpApi` definition: `HealthGroup` (`GET /health`), `AuthGroup` (`POST /auth/register` with `.middleware(RegisterRateLimit)`, `POST /auth/login` with `.middleware(LoginRateLimit)` **and** an explicit `.addError(TooManyRequests)` — the middleware raises 429 for the per-IP window, the handler raises it for the per-username lockout), `UsersGroup` (`GET /users/me`, `.middleware(Authorization)`). Both `/auth/*` endpoints also `.addError(PayloadTooLarge)` — purely so the 413 is in the OpenAPI document; it is raised by the api-level middleware, not by a handler.
- `src/api/AuthMiddleware.ts` — `Authorization` = `HttpApiMiddleware.Tag` with `security: { bearer: HttpApiSecurity.bearer }`, provides `CurrentUser`, fails with `Unauthorized`. `AuthorizationLive` resolves `JwtConfig` once at layer-build time and closes over it — see gotcha below.
- `src/api/RateLimiter.ts` — the `RateLimiter` service: per-IP fixed windows for `login`/`register`, plus a per-username lockout with exponential backoff (threshold → base delay, doubling, capped) that a successful login clears. All limits come from `Config` (`RATE_LIMIT_*`), state is two `Map`s swept on a 60s-ish lazy schedule. **In-process state: correct for one replica, wrong for several** — more than one instance means moving this behind a shared store, keeping the same interface.
- `src/api/RateLimitMiddleware.ts` — `LoginRateLimit`/`RegisterRateLimit` `HttpApiMiddleware.Tag`s failing with `TooManyRequests`, plus `RateLimitLive`. Same closure trick as `AuthorizationLive` (see gotcha). `X-Forwarded-For` is only read when `TRUST_PROXY=true`; otherwise the socket address is used, because a forgeable header would hand every request its own bucket.
- `src/api/AuthLive.ts` — register relies on the `users.usernameLower` `UNIQUE` constraint (catches the constraint-violation error and maps it to `UsernameAlreadyInUse`) rather than a check-then-insert `SELECT`, which would race under concurrent registrations for the same username (verified: pre-fix, concurrent duplicate registrations could 500 instead of 409). See gotcha below on how the error is detected post-Drizzle-migration. Both handlers go through `normalizeUsername`: register writes it to `usernameLower`, login looks up by it. Login calls `RateLimiter.checkUsername` **before** the DB lookup so a locked account costs no argon2id work, and records the failure for unknown usernames too so a 429 never reveals whether an account exists.
- `src/api/UsersLive.ts` / `src/api/HealthLive.ts` — remaining `HttpApiBuilder.group(Api, "<name>", handlers => handlers.handle(...))` implementations. DB access via Drizzle's query builder (`db.select()/.insert()` against `src/db/schema.ts`'s `users` table) against the `Db` tag, no raw SQL.
- `src/api/BodyLimit.ts` — the request body size cap. `MAX_REQUEST_BODY_BYTES` (default 8 KiB) is enforced two ways: a `Content-Length` over the limit is answered 413 before a byte of body is read, while a body without one (chunked / HTTP/2) is read here with a running byte count and abandoned once it passes the limit. In the second case the bytes that did fit are handed downstream through an `Object.create`-based `HttpServerRequest` wrapper whose `stream`/`text`/`json`/`urlParamsBody`/`arrayBuffer` serve the buffer instead of the (now consumed) socket. `BodyLimitLive` is an `HttpApiBuilder.middleware` layer, not an `HttpApiMiddleware.Tag` — see gotcha below.
- `src/api/SecurityHeaders.ts` — the security response headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, CSP, and HSTS). Two CSPs, picked per response by `Content-Type`: `default-src 'none'` for JSON, and a relaxed one allowing inline script/style for the one HTML route (`/docs`, whose Swagger bundle is inlined into the page). Verified in Chromium that the docs page still renders and "Try it out" still works under it. HSTS (`HSTS_MAX_AGE_SECONDS`, default one year, `0` disables) is emitted **only** for requests that arrived over HTTPS — `request.originalUrl`'s scheme, or `X-Forwarded-Proto` when `TRUST_PROXY=true` — so a plain-HTTP deployment is never pinned to a scheme it can't serve. Applied via `HttpApp.appendPreResponseHandler`, not by mapping the app's success channel — see gotcha below.
- `src/api/ApiLive.ts` — `HttpApiBuilder.api(Api)` with `SecurityHeadersLive`/`BodyLimitLive`/`AuthLive`/`UsersLive`/`HealthLive`/`AuthorizationLive`/`RateLimitLive`/`JwtConfigLive` provided, and `RateLimiterLive` provided last so the middleware and the login handler share one limiter instance. The two api-level middlewares are nested `SecurityHeadersLive.pipe(Layer.provide(BodyLimitLive))` — see the ordering gotcha below. Extracted out of `Server.ts` so `test/api.test.ts` can reuse the exact same handler wiring (only swapping in an in-memory DB) instead of duplicating the composition.
- `src/Server.ts` — provides `ApiLive` and `DatabaseLive` into `HttpApiBuilder.serve(...)` + `HttpApiSwagger.layer({ path: "/docs" })` + `BunHttpServer.layer({ port })`, then `BunRuntime.runMain(Layer.launch(HttpLive))`. The serve middleware is `app => HttpMiddleware.logger(cors(app))`; `HttpMiddleware.cors` reads a comma-separated `CORS_ORIGINS` allowlist and falls back to allowing every origin when it's unset (the frontend runs on a different port in dev).
- `scripts/generate-openapi.ts` — `OpenApi.fromApi(Api)` serialised to `web/api.json` (committed). CI regenerates it and `git diff --exit-code`s, so a backend contract change that skips `bun run openapi:generate` fails the build.
- `drizzle.config.ts` — `drizzle-kit` config (dialect `sqlite`, schema path, `out: "./drizzle"`); reads `DB_FILENAME` for its `dbCredentials.url` (only used by the CLI, not at runtime).
- `test/domain/*.test.ts` — unit tests: `Schema.decodeUnknownSync` for payload validation, `Effect.runPromise`/`Effect.runPromiseExit` for the password/JWT helpers.
- `test/api.test.ts` — integration test built on `HttpApiBuilder.toWebHandler`, see gotcha below. It disables rate limiting through a `ConfigProvider` (see gotcha) since every request in the file shares one client address.
- `test/rate-limiter.test.ts` — unit tests for `RateLimiter` against a `TestClock` + a `ConfigProvider.fromMap`, so window expiry and the backoff ladder are asserted without sleeping.
- `test/body-limit.test.ts` — integration test for the body cap: 413 on both the declared-length and the streamed (no `Content-Length`) path, 413 taking precedence over the 400 an invalid payload would get, and normal-sized bodies still working over both paths.
- `test/auth-rate-limit.test.ts` — integration test for the HTTP wiring: 429 status, `Retry-After` header, lockout beating a correct password, and unknown usernames locking out identically.
- `test/security-headers.test.ts` — integration test for the response headers. Mounts `HttpApiSwagger.layer` into the test wiring too (`Layer.provideMerge`, so `Api` stays in the output for `toWebHandler`) so the JSON-vs-document CSP split is covered. The assertions that earn their keep are the non-handler responses — 401, 404, 413 — plus the HSTS scheme/`TRUST_PROXY` matrix.
- `.github/workflows/ci.yml` — two jobs. `check` runs `format:check`, `lint`, `typecheck`, `test` plus two freshness checks at the repo root (`web/api.json`, and `drizzle/` vs `src/db/schema.ts` — the latter asserts on `git status --porcelain drizzle` rather than `git diff --exit-code`, because drift shows up as an _untracked_ new migration file); `web` runs `format:check`, `lint`, `build` and the `api.gen.ts` freshness check inside `web/`. Both via `oven-sh/setup-bun` on push/PR to `main`. Workflow-level `permissions: contents: read` (least privilege — `bun install` and the project tooling run on fork PRs, so the token they see must not be able to write), and the Bun version is pinned via the top-level `BUN_VERSION` env var rather than `latest`, so a commit is validated on the same runtime it ships on.
- `renovate.json` — dependency-update config. Everything in both packages belongs to a named group (`effect`, `drizzle`, `react`, `tanstack`, `tailwind`, `vite`, `radix-ui`, `shadcn utilities`, `forms`, `openapi codegen`, `linting`, `typescript`, `runtime types`, `github actions`, `bun runtime`) so related packages arrive in one reviewable PR. A `customManagers` regex entry reads the `# renovate: datasource=docker depName=oven/bun` comment above `BUN_VERSION` in the workflow and treats it as the `oven/bun` image, which is what groups it with the `FROM oven/bun:<version>` line in the `Dockerfile` — **keep that comment if you touch the env block, or the two silently drift apart again**. `typescript` majors are disabled (TS 7, see gotcha below) and `minimumReleaseAge` is 3 days.

## Gotchas hit while building this (don't re-derive)

- **TypeScript is pinned to `5.9.3`**, not the `7.x` that `bun add typescript` installs by default. `typescript-eslint` (as of this writing) hard-errors on TS 7 ("does not support TS 7.0"). If tooling upgrades to support it, fine to bump — otherwise leave pinned.
- **DB failures must not leak into `HttpApiEndpoint` error channels.** Endpoints only declare `UsernameAlreadyInUse`/`InvalidCredentials`/`Unauthorized` as errors; DB failures are infrastructure defects, not domain errors. Drizzle's `bun-sqlite` driver is synchronous and throws on failure rather than returning an Effect, so handlers wrap calls in `Effect.try(() => db...get())`, which produces an `UnknownException` failure with the original thrown error preserved as `.cause`. Handlers then `Effect.catchAll` that: `AuthLive.ts`'s register handler inspects `error.cause.code === "SQLITE_CONSTRAINT_UNIQUE"` (bun:sqlite attaches `.code` to constraint-violation errors) to distinguish the expected duplicate-username case (→ `UsernameAlreadyInUse`) from everything else (→ `Effect.die`, generic 500); every other query just does `Effect.catchAll(Effect.die)` unconditionally since there's no expected-error case to carve out.
- **`HttpApiMiddleware.Tag` handlers get _no_ extra context** — for a security middleware the `bearer: (token) => Effect<...>` function's requirement type is pinned to `HttpRouter.HttpRouter.Provided`, and a plain (non-security) middleware is pinned the same way (`HttpApiMiddleware<Provides, E> extends Effect<Provides, E, HttpRouter.HttpRouter.Provided>`), so neither can `yield*` a service like `JwtConfig` or `RateLimiter` directly. Fix used here, in both `AuthorizationLive` and `RateLimitLive`: build the handler inside `Layer.effect(Tag, Effect.gen(...))`, resolve the service there (that's the _layer's_ R, satisfied when the layer is composed), and close over the resolved value.
- **A body size limit can't be an `HttpApiMiddleware.Tag`.** Capping the body means (a) rejecting before the payload is decoded and (b) replacing `HttpServerRequest` for everything downstream, and a tag-based middleware can only do the first — it contributes to the handler's error channel, not to its context (only its declared `provides` service). `HttpApiBuilder.middleware(...)` takes a plain `HttpMiddleware` (`(app) => app'`), which can `Effect.provideService(app, HttpServerRequest, wrapped)`. It is provided into `ApiLive` rather than applied in `Server.ts`'s `serve` callback so `toWebHandler` in the tests goes through the identical wiring — `HttpApiBuilder.middleware`'s layer and `toWebHandler` both pull in the same `HttpApiBuilder.Middleware.layer`, which layer memoisation collapses into one instance.
- **An api-level middleware only sees the responses in the app's _success_ channel.** A router 404 (`RouteNotFound`) and a failing `Authorization` middleware both leave the api app as _failures_ and are only turned into responses later — the 404 in `HttpApp.toHandled`, the 401 in the `Effect.catchAllCause` that `HttpApiBuilder.httpApp` applies _outside_ `apiMiddleware`. So `Effect.map(app, setHeaders)` silently misses both (verified: that was the first version of `SecurityHeaders.ts`, and the 401/404 tests failed). `HttpApp.appendPreResponseHandler` is the fix — `toHandled` runs pre-response handlers on the error path as well as the success path, which is also why `RateLimiter` uses it for `Retry-After`.
- **Api-level middleware nesting order is build order, and `Layer.provide` is how you pin it.** `HttpApiBuilder.Middleware`'s `add` composes as `(app) => f(prev(app))`, so the _last_ layer built ends up outermost — and sibling layers provided to `HttpApiBuilder.api(Api)` have no guaranteed order between them. `SecurityHeadersLive.pipe(Layer.provide(BodyLimitLive))` forces the body cap to build first (the inner layer outputs nothing; this is sequencing, not a dependency). It matters because the header pass only _registers_ a pre-response handler: inside the body cap, the 413 short-circuits before registration and that response goes out bare.
- **`HttpIncomingMessage.MaxBodySize` does not cap JSON bodies.** It reads like a general limit, but the only thing that consults it is `Multipart` — the Bun and web `HttpServerRequest` implementations call `source.text()`/`source.json()` straight through with no size check. `BodyLimit.ts` still sets it (multipart would otherwise be uncapped if an endpoint ever accepts one) but does its own counting for everything else.
- **An oversized request never reaches the per-IP rate limiter.** The body cap is api-level so it runs outside the router, while `LoginRateLimit`/`RegisterRateLimit` are endpoint middleware inside it. A flood of oversized requests therefore burns no rate-limit budget — which is the right way round: rejecting on `Content-Length` is the cheapest response the server has, and the limiter exists to cap expensive work (argon2id), not header parsing.
- **Group/endpoint middleware runs _before_ the request payload is decoded** — `handlerToRoute` applies it around the effect that does the decoding (`applyMiddleware(middleware, Effect.gen(...))` in `HttpApiBuilder`). That's why the per-IP rate limit is middleware and not handler code: a flood of malformed bodies gets rejected just as cheaply as well-formed ones, instead of sailing past to a 400.
- **Response headers can't be declared on an error schema** — `HttpApiSchema.annotations` only carries `status`. To emit `Retry-After` alongside the 429, `RateLimiter` calls `HttpApp.appendPreResponseHandler` on the request fiber just before failing; the handler is read back in `HttpApp.toHandled` _after_ the route effect runs, and applies to the error response too. This is the same mechanism `HttpApiBuilder.securitySetCookie` uses.
- **Test files share one process, so `process.env` bleeds between them.** Anything a test needs to pin (rate limits, in particular) goes through `Layer.setConfigProvider(ConfigProvider.fromMap(...).pipe(ConfigProvider.orElse(() => ConfigProvider.fromEnv())))` provided into the app layer — the `orElse` keeps `DB_FILENAME`/`JWT_SECRET` resolving from the environment as usual. Setting the env var at module scope instead would silently reconfigure whichever file bun happens to run next.
- **`BunHttpServer.layerConfig({ port: Config... })` does not type-check** — `ServeOptions` is a union (`Bun.ServeOptions | TLSServeOptions | ...`) and `Config.Wrap` doesn't distribute over it cleanly, so TS infers `Config<any>` for the whole options object instead of per-field wrapping. Worked around by reading `PORT` from `process.env` directly and passing a plain literal to `BunHttpServer.layer({ port })` — simpler anyway since this is one-time startup config, not a value needed at effect runtime.
- **Effect version**: `Schema` lives in `effect/Schema` (bundled into the `effect` package since 3.x) — there is no separate `@effect/schema` install.
- The OpenAPI JSON is not served at a separate `/docs/openapi.json` route — `HttpApiSwagger.layer()` embeds the spec inline in the `/docs` HTML page (`spec: {...}` in the bundled JS). If a standalone JSON endpoint is ever needed, generate it explicitly with `OpenApi.fromApi(Api)` rather than assuming a URL.
- **`HttpApiBuilder.toWebHandler(layer)` requires its `layer` argument to _output_ `HttpRouter.HttpRouter.DefaultServices`, not merely have them internally satisfied.** `Layer.provide` (or `Layer.mergeAll`, which doesn't wire dependencies between merged layers at all) is the wrong tool here. `test/api.test.ts` builds `Layer.merge(ApiLive.pipe(Layer.provide(DatabaseLive)), BunHttpServer.layerContext)`: `Layer.provide` feeds `DatabaseLive`'s `Db` output into `ApiLive`'s requirement (output stays just `Api`), then `Layer.merge` unions that with `BunHttpServer.layerContext`'s output (`HttpPlatform`/`Etag.Generator`/`BunContext`) so both are visible to `toWebHandler`.
- `toWebHandler` builds its layer/runtime **once**, lazily, on the first `handler()` call, and reuses it (via an internal `Scope`) until `dispose()` is called — confirmed by reading `HttpApp.toWebHandlerLayerWith` in `node_modules`. This is what makes an in-memory SQLite DB (`DB_FILENAME=":memory:"`) work as shared state across sequential requests within one test file — Drizzle's migrator runs once against that same in-memory connection at layer-build time, same as it does against a real file on real startup.
- **`JWT_SECRET` has no default outside `NODE_ENV=test`** — `Auth.ts` branches on `process.env.NODE_ENV === "test"` (which `bun test` sets automatically) to supply a fixed test secret; every other environment requires the real env var or the app fails to start with a `ConfigError` (`Missing data at JWT_SECRET`). Verified by running the server with a stripped env from a different cwd (so Bun's automatic `.env` autoload can't find the project's `.env`).
- **Password hashing cost is also turned down under `NODE_ENV=test`** (`memoryCost: 19, timeCost: 1` vs Bun's real argon2id defaults) — cut the test suite from ~900ms to ~250ms. Don't "fix" this by using the same cost in both — that's the point.
- **The migrations folder path in `Database.ts` is resolved via `new URL("../../drizzle", import.meta.url).pathname`**, not a relative string like `"./drizzle"` — `drizzle-orm/bun-sqlite/migrator`'s `migrate()` resolves relative paths against `process.cwd()`, which breaks as soon as the process is started from anywhere other than the repo root (e.g. `bun test` from a subdirectory, or a packaged binary). `import.meta.url`-relative resolution is cwd-independent.
- **A hand-edit to a generated migration is not a place to keep an invariant — drizzle-kit rewrites it.** Case-insensitive usernames used to be a `COLLATE NOCASE` typed by hand into `0000_*.sql`, because sqlite-core's column builder has no `.collate()`. But drizzle-kit diffs against `drizzle/meta/*_snapshot.json`, and the snapshot has no field for collation, so any later change to `users` that triggers SQLite's table-recreation dance regenerated the column as plain `text NOT NULL` — silently, since the migration still applies cleanly (verified by making `passwordHash` nullable and running `db:generate`; the rebuilt column lost the collation, and the unique index, which inherits it, went case-sensitive with it). The rule generalises: if drizzle-kit's snapshot can't represent it, it will not survive. The fix was to move the invariant into something the snapshot _does_ represent — the `username_lower` column and its `UNIQUE` index — with `normalizeUsername` applied on write and on lookup. Re-verified the same way afterwards: the regenerated recreation carries both.
- **ESLint uses `tseslint.configs.recommendedTypeChecked`** (via `projectService: true` in `eslint.config.mjs`), not the plain `recommended` set — it needs a real tsconfig to type-check against, which is why it caught `bun-types`' `expect(...).rejects.toBeDefined()` being typed as returning `void` instead of a `Promise` (a real mistyping in `bun-types`, not a bug in the test). Worked around in `test/domain/auth.test.ts` by asserting on `Effect.runPromiseExit(...)` instead of `.rejects`, which is also more idiomatic for testing Effect programs.

## `web/` — the React frontend

A **separate package**, not a workspace member: its own `package.json`, `bun.lock`, `tsconfig.json`, `eslint.config.mjs` and `.prettierrc.json`. Run its commands from `web/`. The root's ESLint config ignores `web`, and the root `.prettierignore` does too, so the two toolchains never fight over the same files.

Stack: Vite 8 + React 19, TanStack Router (code-based routes) + TanStack Query, Tailwind CSS v4 (`@tailwindcss/vite`, no `tailwind.config.js`), shadcn/ui primitives, react-hook-form + Zod, `motion` (Framer Motion v12) for animation, `openapi-fetch` + `openapi-typescript` for the API client.

**Product framing**: planq is pitched as shift planning for hospitals, clinics and care teams, so UI copy addresses clinicians and rota administrators, not developers. Only auth + the account view are actually built — the dashboard's "Your next shifts" panel is an explicit empty state saying scheduling is still in development. Don't replace it with mock shifts, and don't write copy that implies unbuilt scheduling features work. Security claims in the marketing column must stay factually true of the code (argon2id hashing, two-hour session expiry) — no invented compliance certifications.

cd web
bun run dev        # :5173, proxies /api/* -> http://localhost:3000
bun run build      # tsc --noEmit && vite build
bun run lint / format / typecheck

### The generated-contract chain

`src/api/Api.ts` → `bun run openapi:generate` (root) → `web/api.json` → `bun run api:types` (web) → `web/src/lib/api.gen.ts` → `web/src/lib/api.ts`. Both generated files are committed and CI diff-checks them. Nothing in the frontend hand-writes a request or response shape.

### File map

- `src/lib/api.ts` — the `openapi-fetch` client. Module-level token slot + `onRequest` middleware attaches `Authorization`; `ApiError` normalises the API's tagged errors (`UsernameAlreadyInUse`, `InvalidCredentials`, `Unauthorized`, `TooManyRequests`, `PayloadTooLarge`, `HttpApiDecodeError`) into user-facing messages — `TooManyRequests` renders the server's `retryAfterSeconds` as a readable wait, and `isRateLimited` marks it as not worth retrying; `request()` also wraps fetch rejections so callers only ever see `ApiError`.
- `src/features/auth/` — `AuthProvider` (session state), `auth-context.ts` (the `useAuth` hook, split out so the provider file only exports a component), `session-storage.ts`, `schemas.ts` (Zod mirrors of the backend's username/password rules), `AuthLayout`/`AuthTabs`, `LoginForm`, `RegisterForm`, `PasswordStrength`.
- `src/features/dashboard/` — `DashboardPage` renders the `/users/me` payload field by field, plus a JWT-`exp` countdown and a raw-JSON disclosure.
- `src/components/ui/` — shadcn/ui primitives (`components.json` present, so `bunx shadcn@latest add …` works).
- `src/components/` — app-specific: `AuroraBackground`, `GlassPanel` (cursor-tracking highlight), `BrandMark`, `PasswordInput`, `FormAlert`, `SubmitButton`, `CopyButton`, `ApiStatusPill`, `NotFoundPage`.
- `src/router.tsx` — route tree. `/login` and `/register` sit under a pathless `_auth` layout route so the card and the sliding tab pill stay mounted between them; `/` is guarded and `_auth` redirects away when already signed in.
- `security-headers.ts` — one definition of the CSP + `nosniff`/`X-Frame-Options`/`Referrer-Policy` set, consumed three ways by `vite.config.ts`: `server.headers` (dev, with `'unsafe-inline'` script and `ws:` added for the React Refresh preamble and HMR), `preview.headers` (the production policy, since `preview` serves the build), and a `transformIndexHtml` plugin that inlines it into `dist/index.html` as `<meta http-equiv>` so a static host with no header config still enforces `script-src`/`connect-src`. `contentSecurityPolicyMeta` strips `frame-ancestors`, which a `<meta>` tag cannot express — so clickjacking protection genuinely does need a real response header in production, which is what `web/README.md` tells the deployer. `Strict-Transport-Security` is deliberately absent (origin-level concern). `VITE_API_BASE_URL`'s origin is folded into `connect-src` at build time.
- `src/index.css` — design tokens (shadcn variable names, dark-only), the `glass` / `glass-subtle` `@utility` recipes, keyframes, and the `prefers-reduced-motion` blanket override. The palette is clinical by intent: three raw tokens `--azure` (primary), `--teal` (accent) and `--mint` feed the aurora, buttons and avatar; nothing else on screen is warm, so amber/red stay meaningful.

### Gotchas hit while building the frontend

- **Auth state must be primed before the first render.** `AuthProvider.tsx` calls `setAuthToken(readSession()?.token)` at _module scope_, not in an effect — otherwise the `/users/me` query fired during mount races the effect and goes out without a bearer header.
- **`RouterProvider context={{ auth }}` is not enough on its own.** Route guards read auth from the router context, which is only sampled when a match is evaluated, so `App.tsx` calls `router.invalidate()` in an effect keyed on `auth.isAuthenticated`. Without it, signing out while on `/` leaves you sitting on the guarded page.
- **`eslint-plugin-react-hooks` v7 ships `configs.recommended` in eslintrc shape** (`plugins` as an array of strings), which flat config rejects with a confusing error. The flat variants live under `configs.flat` — the config uses `reactHooks.configs.flat["recommended-latest"]`.
- **The React Compiler lint rules are strict about two things here**: `react-hooks/set-state-in-effect` flags the 401 → `signOut()` effect in `AuthProvider` (disabled inline with a comment — reacting to a server rejection _is_ external synchronisation), and `react-hooks/incompatible-library` flags `form.watch()` from react-hook-form (fixed properly by using `useWatch({ control, name })`).
- **`form.handleSubmit(...)` returns a promise**, which trips `@typescript-eslint/no-misused-promises` when passed straight to `onSubmit`. Both forms wrap it: `onSubmit={(event) => void form.handleSubmit(...)(event)}`.
- **`throw redirect(...)`** — TanStack Router's guard idiom throws a non-Error object, so `@typescript-eslint/only-throw-error` is turned off for `src/router.tsx` specifically (not globally).
- **`motion.div`'s prop types widen `children`** to include `MotionValue`, which isn't assignable to `ReactNode`. `GlassPanel` narrows it back with `Omit<ComponentProps<typeof motion.div>, "children"> & { children?: ReactNode }`.
- **Aurora blob sizes use `size-[max(70vw,560px)]`**, not plain `vw` — at a 390px phone width, viewport-relative blobs collapse into three small dots and the background goes flat black.
- **`tsconfig.json` sets `allowJs: true`** purely so typescript-eslint's project service can resolve `eslint.config.mjs` when linting itself; without it ESLint errors with "was not found by the project service".
- **`web/` needs its own `@types/node`, and `"node"` in `tsconfig.json`'s `types`.** Only the config files use Node APIs (`vite.config.ts` reads `process.env` and imports `node:url`; `eslint.config.mjs` uses `import.meta.dirname`), but without those types they resolve to `error` types and `recommendedTypeChecked`'s `no-unsafe-*` rules fail. This is invisible during local development — Node walks up and finds `@types/node` via the root package's `node_modules` (a transitive dep of `@types/bun`) — and only fails in CI, where the `web` job checks out and installs `web/` alone. **When debugging a CI-only failure in `web/`, reproduce it by moving the root `node_modules` aside**, not by trusting a green local run.
- The dev server proxies `/api/*` rather than pointing the client at `http://localhost:3000` directly, so the browser stays single-origin in development. CORS on the backend still matters for deployments where the two are served from different hosts.
- **`style-src` cannot drop `'unsafe-inline'`.** React `style` props and `motion`'s per-frame animations write inline `style` attributes. Splitting into `style-src-elem 'self'` + `style-src-attr 'unsafe-inline'` is tighter on paper, but a browser that doesn't know those directives falls back to `style-src` and blocks the attributes — a policy that breaks the UI only on older browsers is worse than one honest `'unsafe-inline'`. `script-src` is the directive that actually protects the `localStorage` token, and that one stays at `'self'`.
- **`vite preview` reports `command === "serve"`**, same as the dev server, so `defineConfig(({ command, isPreview }) => ...)` has to check `isPreview` too — otherwise `preview` (which serves the real build) gets the dev CSP relaxations and the strict policy is never actually exercised before production.
- **The dev/preview CSP is worth checking in a real browser, not by reading it.** A too-strict policy fails silently — blocked inline styles just render wrong. Chromium is preinstalled here (`/opt/pw-browsers/chromium`); the check that mattered was driving `/register` through to the dashboard on the dev server and loading the `preview` build, both with zero console errors or warnings.
